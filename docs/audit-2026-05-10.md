# Gifted — End-to-end project audit

**Date:** 2026-05-10
**Auditor:** Architect (Swarm)
**Scope:** Read-only review of repo state vs. strategy. No code changes.

## 1. State of the project

### Strategy (per `research/02-niche-heatmap-findings.md`)
- **Profitable niche growth at $2 fixed margin**, premium positioning.
- **SEM-led acquisition**, supplemented by SEO landing pages (mandatory — SEM-only is too thin) and an email loop.
- **Reloadly** for the gift-card catalog; **Stripe per-country** for payments.
- First-wave geography: **fi-FI, en-IE, en-AU, ar-AE, ar-SA, pl-PL, el-GR, en-MT, en-NZ** — Finland is the headline market; Nordics outside FI are inventory-blocked, US/UK/DE/FR are math-blocked, most of CEE is inventory- or Stripe-blocked.
- Soft-launch plan: $300/mo cap on Bing Ads, Finland × top-5 brands first.

### What is actually built today

**Done and merged into `main`:**
1. **Reloadly catalog integration is real** (`lib/reloadly/client.ts` + `lib/giftcards/service.ts`). OAuth, products fetch, redeem instructions, order placement — all wired against the real API. Sandbox mode toggled by `RELOADLY_ENVIRONMENT`.
2. **Order persistence is real** (`lib/orders/repository.ts` — Upstash Redis with a 7-day TTL; in-memory fallback for local dev). The earlier "in-memory `Map` on serverless" defect from the Opus review is fixed.
3. **Server-owned order lifecycle**: `POST /api/orders` (create pending), `GET /api/orders/:id` (read), `POST /api/reloadly/order` (server-side validate + fulfill). The browser cache is a non-authoritative optimistic hint only.
4. **Rate limiting** via Upstash (`lib/rate-limit.ts`), graceful fail-open on Redis blips.
5. **Sentry** wired with PII scrubbing.
6. **i18n routing for 9 first-wave locales** (`lib/i18n/config.ts`, `app/[locale]/...`, middleware-based locale detection). RTL handling for Arabic. Locale switcher in header.
7. **Per-locale × per-brand landing-page generator** (`app/[locale]/buy/[brand]/page.tsx`, `lib/landing-pages/{brands,copy,viable-cells,slug}.ts`). 20 hand-curated brands, build-time viability filter against the live Reloadly catalog, hand-translated copy in 6 languages (en, fi, ar, pl, el; FAQ + hero + description). PR #5 merged 2026-05-09.
8. **Brand logo assets** (`public/brand/`) — wordmark SVG + PNG @1x/2x/4x/6x in transparent + white. Logo applied in header/footer.
9. **E2E coverage** for browse, product detail, checkout flow, i18n, landing pages, fold/UX, visual regression (Playwright, 8 spec files).

**Repo hygiene is good now.** The "186 swarm deliverable markdown files" from the Opus review have been deleted. Root has README, OPUS47_CODE_REVIEW, P0_FIXES_REPORT, and seven legacy `*_SUMMARY.txt` files (low priority cleanup).

### What is **not** built — the launch blockers

1. **Payment processing does not exist.** This is unchanged from the Opus 47 review (2026-04-18) — it was "out of scope" then and is still missing now. Strategic implication: **Stripe per-country is in the strategy doc and on the FAQ copy in 6 languages, but the codebase has zero Stripe code, zero `/api/stripe/*` routes, zero webhook handler, zero PaymentIntent flow.** `POST /api/reloadly/order` will happily fulfill a real gift card for $0 to anyone who can hit the endpoint with a valid orderId. **This is the single largest gap.** It is also the one the strategy depends on the most (Stripe payment-method matrix per country was Phase 1).
2. **No SEO scaffolding** despite Phase 1 Task 3 being briefed in `research/swarm-tasks/03-seo-scaffolding.md`. No JSON-LD `Product`/`Offer`/`Breadcrumb`, no `app/sitemap.ts`, no `app/robots.ts`, no `hreflang` link tags. Without this, the SEO-compounding-engine half of the business case (the "10% capture vs. 2%" lever that takes the model from $1.9k/yr to $9.5k/yr) doesn't compound.
3. **No email loop.** Per the model in the heatmap doc, the email loop is one of the three multipliers (margin × capture × loop) that turn the project into a $30–50k/yr business. There is no email-capture component, no transactional email provider wired (Resend / SendGrid env vars exist in `.env.example` but nothing reads them), no welcome / abandoned-cart / repeat-buyer flow.
4. **No analytics.** PostHog env vars are in `.env.example`, but nothing imports `posthog-js`. We will not be able to measure CVR by (locale × brand) at launch — which is the exact thing we need to know to know whether the business case holds.
5. **No production Reloadly access verified.** `.env.example` and `lib/reloadly/client.ts` default to sandbox. The research doc explicitly flags: *"Sandbox catalog can differ from production — needs upgrading."* Phase 0 research called this out as one of the biggest open questions; I have no evidence it's been resolved.
6. **No real Reloadly margin schedule confirmed.** Strategy assumes $2 effective margin. Research doc flags Reloadly per-brand commercial terms as "the single biggest unknown." Without this, the entire CPC × CVR × margin model is speculation.
7. **No deployment target verified.** `.vercel/` exists locally but I have not confirmed any production deployment URL is live. The stack is Vercel-ready (Next.js 14 App Router, Upstash, Sentry, edge middleware) but I see no recorded deploy URL or domain.

### Build / test posture

- TypeScript: clean (`P0_FIXES_REPORT.md` reports `tsc --noEmit` clean except pre-existing test errors in `rate-limit.security.test.ts`).
- Build: `npm run build` clean per the same report. Bundle ~135KB first-load JS.
- E2E: 8 Playwright suites; landing-pages and i18n suites are recent (PR #5) — recommend running locally before tagging "green."
- Unit tests: limited (`lib/__tests__/landing-pages.test.ts`, `i18n.test.ts`, `rate-limit.security.test.ts`, `lib/orders/__tests__/repository.test.ts`).

## 2. Prioritized task list

Effort estimates assume swarm wall time (architect → coder → tester → reviewer → integrator), not human time. Each task should be a separate PR.

### P0 — Launch blockers

#### P0-1 — Stripe payment integration (per-country payment-method matrix) — **2–4 days swarm time**
Must come before anything else. Without it, the site cannot legally take money and the Reloadly route is a free dispenser.
- Add `lib/payments/stripe.ts` (server-only Stripe client).
- New routes: `POST /api/payments/intent` (creates PaymentIntent for an `orderId`), `POST /api/webhooks/stripe` (signature-verified, idempotent — only this route flips an order to `paid` and triggers Reloadly fulfillment).
- Move Reloadly fulfillment **out** of the user-facing route and **into** the webhook handler. Replace `POST /api/reloadly/order` with an internal-only fulfillment function. The user's checkout submit creates a PaymentIntent and confirms it; Reloadly is only called after `payment_intent.succeeded` arrives via webhook.
- Per-country payment-method matrix per the research doc: Stripe Elements with `automatic_payment_methods: { enabled: true }` is the right starting point. Validate that **iDEAL** (NL — not in first wave but cheap), **MobilePay** (FI — relevant), **Mada** (SA), and **Apple Pay / Google Pay** (all locales) actually surface in the Payment Element for the test mode of each country.
- Idempotency: PaymentIntent creation should be idempotent on `orderId` (use Stripe's `idempotencyKey`). Webhook handler must be idempotent on `event.id`.
- Update success page copy: only show "Order confirmed" once the webhook has flipped the order to `paid`. Until then show a "Payment processing" state.
- **Rationale:** This is the single largest delta between "demo site" and "shippable business." It also unblocks every other revenue-generating task below.

#### P0-2 — Confirm Reloadly production access + per-brand margin schedule — **0.5 day, manual**
- Svante to confirm with Reloadly account contact: (a) production API access, (b) the actual % discount Reloadly pays per brand × country. Without this the $2 margin assumption is unfalsifiable.
- Action: Svante calls Reloadly. Add result to `research/03-reloadly-commercial-terms.md`.
- **Rationale:** Strategy depends on it. If real margin is closer to $1, the model closes for almost every cell except Finland-Steam.

#### P0-3 — Wire PostHog (or Plausible) for funnel + CVR measurement — **0.5–1 day swarm time**
- Install `posthog-js` and a thin `lib/analytics.ts` wrapper.
- Track: `page_view`, `country_selected`, `brand_viewed`, `denomination_selected`, `delivery_method_selected`, `checkout_started`, `payment_succeeded`, `payment_failed`. All scoped by `locale` + `brand` so we can see CVR per cell.
- Add a privacy-respecting cookie banner (we have RTL/Arabic locales — check it works in `dir="rtl"`).
- **Rationale:** Without this we cannot verify or refute the CVR model. The whole strategy is "test small in Finland and confirm or refute the thesis" — that is impossible without analytics.

### P1 — Strategic enablers (do before SEM spend goes up)

#### P1-1 — SEO scaffolding (Task 3 from the research backlog) — **1 day swarm time**
Brief already exists at `research/swarm-tasks/03-seo-scaffolding.md`.
- `app/sitemap.ts` enumerating `/`, `/[locale]`, `/[locale]/buy/[brand]` for every viable cell.
- `app/robots.ts` with a sensible disallow set.
- `<link rel="alternate" hreflang="...">` tags on every locale-aware page (mandatory for the 9-locale matrix to work in Google).
- JSON-LD `Product`, `Offer`, `Breadcrumb` injected on `/[locale]/buy/[brand]` pages.
- **Rationale:** The research doc is unambiguous: "SEO landing pages are mandatory" to lift the model from $1.9k to $9.5k/yr. The pages exist; the metadata to make Google index and rank them does not.

#### P1-2 — Email infrastructure + receipt + recipient delivery confirmation — **1–2 days swarm time**
- Wire Resend (it's already in `.env.example`).
- Transactional emails: customer receipt, payment-failed apology, recipient gift-card-on-its-way preview (Reloadly emails the actual code separately — that's fine, but we should also send a "your gift is coming" preview from us with the gift message rendered nicely).
- Email-capture component on landing pages (one of the three margin-multiplier levers).
- **Rationale:** Email loop is one of three explicit levers in the model. Plus, today the success page is a half-truth: we say "the code was emailed" but we're trusting Reloadly to do that, with no visibility.

#### P1-3 — Payment-method matrix audit per launch country — **0.5 day, manual + light code**
- For each launch country (FI, IE, AU, AE, SA, PL, GR, MT, NZ), confirm via Stripe Dashboard test mode which Payment Element methods will surface.
- Document in `docs/payment-methods-by-country.md`.
- For SA in particular: verify Mada works; if not, document the gap (Stripe SA + Mada has been historically gnarly).
- **Rationale:** Strategy says "Stripe per-country" but the current Stripe defaults may not match local payment-method expectations (e.g. Finns expect MobilePay; Saudis expect Mada; Aussies expect Apple Pay heavily on mobile).

#### P1-4 — Cleanup (legacy summary files in repo root) — **0.5 hour manual**
- Delete: `BUG_FIXES_SUMMARY.txt`, `CODER_EXECUTIVE_SUMMARY.txt`, `PRODUCT_CARD_FIX_SUMMARY.txt`, `QUICK_FIX_SUMMARY.txt`, `REVIEWER_EXECUTIVE_SUMMARY.txt`, `SWARM_COMPLETION_SUMMARY.txt`, `TESTER_COMPLETION_SUMMARY.txt`, `TESTING_COMPLETE.txt`, `TESTING_COMPLETE_SUMMARY.txt`. These are leftover swarm artifacts already cleaned at one level — these seven survived.
- Keep: `README.md`, `OPUS47_CODE_REVIEW.md`, `P0_FIXES_REPORT.md`, this audit.
- **Rationale:** Cosmetic but it makes the repo more credible to anyone (e.g. a future reviewer or hire) opening it cold.

### P2 — Hardening before serious spend

#### P2-1 — Webhook + payment idempotency + order state machine tests — **1 day**
Once P0-1 lands, write integration tests against Stripe test mode that exercise: success, failure, late webhook, duplicate webhook, replay attack (wrong signature). Order state machine is small; this should be unit-testable.

#### P2-2 — Sentry + PostHog dashboards for key business metrics — **0.5 day**
Build a single PostHog dashboard with: cell-level CVR, cell-level funnel drop-off, payment failure rate by country, average margin per checkout. This is what the "first $300 spend" loop depends on for go/no-go.

#### P2-3 — Fraud + abuse — **1–2 days**
- Reloadly orders are bearer-instrument. A successful chargeback after fulfillment costs us ~$50 net. Once payments are live, even a small fraud rate breaks the unit economics.
- Stripe Radar default rules + 3DS2 enforcement on `>$30` orders is a sensible starting point. Document the policy.
- IP-based velocity limits (already partly there via the rate limiter, but only for unauth'd order creation).

#### P2-4 — A11y + RTL polish — **0.5 day**
- Run axe / Lighthouse a11y on a representative LTR (en-IE) and RTL (ar-AE) page. Fix anything WCAG-AA-blocking.
- Manually verify the Arabic landing pages render with correct mirroring.

#### P2-5 — Single-source service-fee policy — **0.5 hour**
Old Opus review flagged two service-fee formulas in two files. The PR-merge log says it's been resolved (`chore(currency): document calculateServiceFee as the single source of truth`). Re-confirm and add a unit test that pins it. Trivially cheap insurance.

### P3 — Things to consider but not commit to yet

- **Cohort-1 / Cohort-2 customer accounts.** Strategy is guest checkout; that's right for v1. Add accounts only if data shows repeat-purchase intent we can't capture via email-only.
- **Currency conversion.** Today each locale sells in its own currency from the Reloadly catalog. Cross-currency upsell is out of scope.
- **Promo codes.** Tempting for SEM landing pages, but every promo code reduces margin in a thesis where margin is already the binding constraint. Hold.

## 3. Risks, gaps, contradictions worth Svante's attention

### 3.1 The biggest risk: **the strategy promises Stripe but the codebase has no Stripe**
The README and FAQ copy in 6 languages tell users their cards are processed by Stripe. They are not. They are not processed by anything. **Anyone who finds the production URL of `/api/reloadly/order` and constructs a valid `orderId` (either by creating one via `POST /api/orders` or by guessing — they're UUIDs but the surface is small) can drain the Reloadly balance.** The README says "mock data only" but the codebase has graduated past that — the Reloadly client is real, the orders are real, only payment is missing. This needs a hard guard before any URL is shared publicly. Today, the cheap mitigations are: (a) keep the site behind Vercel password protection until P0-1 lands, (b) keep Reloadly in **sandbox** mode, (c) do not point a domain at the deployment.

### 3.2 The second biggest risk: **the strategy depends on a Reloadly margin number nobody has verified**
The heatmap doc is honest about this — "the single biggest unknown." If Reloadly's actual per-brand commission ends up below $2 average, the strict-base-case is *negative*, not just small. The whole P1 plan should be paused on a 30-minute call with the Reloadly account contact.

### 3.3 The strategy doc was written against the **sandbox** catalog
2,961 SKUs, 169 countries, 41% Fortnite. The production catalog might be richer (or thinner). Every viable-cell number — from "Finland is the unicorn" to "skip Sweden, no inventory" — is conditioned on this sandbox data. Production access changes the inputs.

### 3.4 SEM strategy is precise but the analytics plumbing to validate it is missing
The Phase 2 plan is "spend $300/mo on Bing Ads in Finland × top-5 brands and confirm/refute the thesis." Without PostHog (P0-3) we will literally not know whether CVR was 1% or 6%, or whether the failure was at landing, denom, checkout, or payment. This is one cron away from being a real problem when ad spend starts.

### 3.5 The "Lemon Squeezy" trap is mostly cleaned up but leaves residual confusion
The README still has a long "Lemon Squeezy integration guide" section. The codebase has dropped Lemon Squeezy entirely in favor of Stripe (per FAQ copy). This contradiction should be cleaned up — the README is one of the first things any contributor reads, and right now it documents the wrong payment provider.

### 3.6 The 9-locale launch may be too wide for the first $300 of spend
Research doc says "Finland × top-5 brands first; only expand if Finland validates." The codebase ships 9 locales × 20 brands = up to 180 landing pages. That's the right asset to *have* for SEO, but it's also a maintenance and translation surface area cost before the model is validated. If Finnish CVR underperforms, the cost of the other 8 locales is sunk.
- **Recommendation:** ship all 9 locales (asset value for SEO), but route SEM spend only to fi-FI for the first 30 days. Use `noindex` to cull the long tail if it doesn't earn its keep — but don't take the locales out of the codebase.

### 3.7 The P0_FIXES_REPORT and OPUS47_CODE_REVIEW are stale-ish
Both written 2026-04-18. A lot has happened since (i18n, landing pages, repo cleanup). The "unshippable" verdict was for that snapshot — the project has materially improved. The architectural verdict has moved from "D−, not shippable" to "C/B−, missing one critical layer (payments) and several enablers (SEO, email, analytics)." When P0-1 lands, this becomes a launch-ready stack.

### 3.8 No production deployment URL exists in the workspace
I see `.vercel/` configuration but no recorded production URL, no DNS, no domain. Before any of the SEM plan can run, there needs to be a `gifted.<tld>` URL, and that URL needs to **not** be reachable for purchases until P0-1 is done.

## 4. One-paragraph state of the project

The Gifted codebase has cleared most of the architectural and infrastructure debt that made the April Opus review file it as unshippable: orders are persistent in Upstash Redis, the order lifecycle is server-owned, Reloadly is real, Sentry is wired with PII scrubbing, rate limiting is in place, i18n routing is live for 9 first-wave locales, the per-locale × per-brand landing-page generator is shipped against the live Reloadly catalog, and brand assets are applied across the surface. **The single critical layer missing is payments.** The README and FAQ promise Stripe, the strategy depends on Stripe per-country, but the codebase has zero Stripe code — `POST /api/reloadly/order` is currently a free gift-card dispenser if anyone finds it. Beyond payments, the three other "must do before SEM spend" items are SEO scaffolding (sitemap/robots/hreflang/JSON-LD), analytics (PostHog), and confirming the production Reloadly catalog + per-brand margin schedule with the Reloadly account contact. With P0-1 (Stripe) and P0-2/P0-3 (margin verification + analytics) closed — call it 3–5 days of swarm work plus a phone call — this is a launch-ready niche-SEM business, ready to validate or refute the Finland thesis at the planned $300/mo cap. Without P0-1, any URL that goes live is a money-losing fuse waiting to be lit.
