CONFIDENTIAL · PRE-LAUNCH AUDIT

Gifted — Pre-Launch Review

Repository: gifted-project · Tag: d4e2e23 · Stack: Next.js 14.2.18 (App Router) · TypeScript · Upstash Redis · Reloadly · Sentry · Reviewed: 2026-05-22

Executive Summary

TL;DR. Gifted is a polished, well-typed, internationalized Next.js front end sitting on top of a checkout flow that is not yet safe to put in front of paying customers. The single largest issue is unchanged from the April code review: there is no payment processor in the loop — the “Complete Purchase” CTA charges nothing and dispenses a real Reloadly gift card. Several structural blockers remain on top of that: no Upstash Redis credentials in Vercel production (so the order repo falls back to per-instance in-memory Map), no security headers, no legal pages despite the footer linking to them, an IDOR-style order lookup, and four npm audit vulnerabilities including a Next.js critical (cache poisoning) and high (DoS via Server Components).
LAUNCH READINESS: RED — DO NOT LAUNCH
At least one finding (no payment capture) makes paid launch financially catastrophic. Resolve all five must-fix items below before any external traffic.

Top 5 must-fix-before-launch

  1. Wire a real payment processor before /api/reloadly/order can be reached.
    Right now the checkout button calls processOrder() → POST /api/reloadly/order → Reloadly fulfillment, with no payment capture anywhere in between. Self-acknowledged in lib/orders/api.ts:64–67: “will happily charge $0 to the customer and hand out a real gift card — do not expose publicly.” This is the same blocker the April Opus code review flagged; P0_FIXES_REPORT.md confirms it is still open.
  2. Set UPSTASH_REDIS_REST_URL + UPSTASH_REDIS_REST_TOKEN in Vercel production.
    Verified via vercel env ls production — only Reloadly creds are present. Without Redis env, lib/orders/repository.ts:178–199 falls back to an in-memory Map, which loses orders across serverless instances. Same applies to rate limiting: lib/rate-limit.ts:93–100 explicitly disables rate limiting in production when Redis is absent — endpoints become fully open.
  3. Add security headers (CSP, HSTS, X-Frame-Options, Referrer-Policy, Permissions-Policy).
    next.config.mjs has no headers() export and middleware.ts sets no response headers. A gift-card site with no CSP and no clickjacking protection is a no-go. ~30 min to add.
  4. Write and publish legal pages: Terms, Privacy, Cookie Policy, Refund Policy. Stop linking to 404s.
    Footer (components/layout/Footer.tsx:120,128) links to /[locale]/terms, /[locale]/privacy, /[locale]/help, /[locale]/contact, /[locale]/faq, /[locale]/about — none of which exist under app/[locale]/. They all return the localized 404. GDPR (EU locales: fi-FI, en-IE, pl-PL, el-GR, en-MT) requires Privacy + Cookie at minimum, and gift-card resale typically requires explicit Terms and a No-Refund clause.
  5. Rotate the Reloadly credentials that have been sitting in .env.local and in dev/swarm contexts.
    The RELOADLY_CLIENT_SECRET in .env.local has been in committed development artifacts and shared agent contexts for 41+ days (vercel env ls shows it was uploaded 41d ago). The file itself is .gitignore'd, but a credential that has been on multiple disks and agent inputs should not be the one that touches production. Rotate in the Reloadly dashboard, push the new value to Vercel, redeploy.

Blocker
Likelihood × Impact
High × High — checkout pages can be iframed and overlaid; reflected XSS payload from any future input would not be blocked.
Current state
Zero security headers (verified: no headers() in next.config.mjs, no header logic in middleware.ts).
Mitigation
See checklist 1.2. CSP + HSTS + X-Frame-Options: DENY + Referrer-Policy + Permissions-Policy.
Effort

Blocker
Likelihood × Impact
Medium × High — cache poisoning of RSC responses (GHSA-wfc6-r584-vfw7, critical) is publicly exploitable. App Router CSP-nonce XSS (GHSA-ffhc-5mcf-pf4q) is relevant once we add a real CSP.
Current state
next@14.2.18; 4 advisories open (npm audit --production).

Medium

Low × Medium today (guest checkout, no session) — rises to High when accounts are introduced.

R-SEC-06 · Dependency-chain exposure (Upstash, Reloadly, Sentry)

Medium
Likelihood × Impact
Low × High — a Reloadly outage means the catalog and the fulfillment path both fail; a Sentry outage degrades observability silently.
Current state

2.2 Payment Fraud (Stolen Cards)

Foundational note. There is currently no payment processor in the flow at all, so "fraud signals" cannot be evaluated against a real implementation. Every recommendation below is contingent on first wiring a PSP (R-PAY-01). The whole class of fraud risk only becomes real on the day charges start.

R-PAY-01 · No payment capture

Blocker
Likelihood × Impact
Certain × Catastrophic — every successful checkout costs the business the full card value.
Current state
processOrder in lib/orders/api.ts:64–82 calls Reloadly directly. No PaymentIntent, no Lemon Squeezy webhook gate (despite Lemon Squeezy being in .env.example).
Recommendation
Stripe Payment Element with setup_future_usage=off, 3DS = required for any non-EU card and "automatic" for EU (SCA-compliant). Webhook payment_intent.succeeded → Reloadly call.
Effort
M 3–5 engineer-days end-to-end including webhook signature verification, idempotent fulfillment, and the refund path.

R-PAY-02 · No fraud signals captured at checkout

Blocker
Likelihood × Impact
High × High — gift-card marketplaces are top targets for stolen-card monetization (fast, anonymous, irreversible).
Current state
Checkout collects only email. No device fingerprint, no IP, no AVS/CVV results, no behavioral signals, no email-age check.
MVP signals to capture
  • Device fingerprint (Stripe Radar / Fingerprint.com) — required to differentiate one buyer from a card-testing botnet.
  • IP ↔ billing country mismatch.
  • Email domain reputation (e.g. emailable, kickbox) — reject disposable domains for orders > €25.
  • Velocity: same card > 1 order/24 h, same email > 3 orders/24 h, same IP > 5 orders/24 h.
  • AVS + CVV result codes from the PSP — reject on AVS_NO_MATCH for orders > €50.
Mitigation
Enable Stripe Radar (free with Stripe Payments). Add custom Radar rules for gift-card velocity. Reject all sub-3DS Visa/MC transactions over €25.
Effort
M 2–3 days of Radar tuning + 1 sprint of monitoring.

R-PAY-03 · 3DS / SCA not enforced

High
Likelihood × Impact
High × High — without 3DS, the liability for fraudulent transactions stays with the merchant (you).
Current state
No PSP, so no 3DS. EU launch locales (fi-FI, en-IE, pl-PL, el-GR, en-MT) require SCA under PSD2.
Mitigation
Configure Stripe to require 3DS = automatic in EU (PSP picks based on PSD2 rules) and force any for non-EU cards > €25. Liability shifts to issuer.
Effort
S Configuration in Stripe + 1 h test coverage.

R-PAY-04 · No velocity limits / order ceilings

High
Likelihood × Impact
High × High — fraudsters automate to maximize cards bought per stolen card before block.
Current state
No per-card / per-email / per-IP daily ceiling. fixedDenominations top out at the brand's max but a single card can buy 100×€100 Amazon GBs in a minute.
Mitigation
Server-side limits keyed in Redis:
  • Per email: max €200 / 24h · max 3 orders / 24h.
  • Per IP: max €500 / 24h · max 8 orders / 24h.
  • Per PaymentMethod fingerprint (Stripe gives this): max €200 / 7d on first-touch.
  • Per recipient email: max 2 distinct sender emails / 7d (catches "scrub" pattern).
Tunable from config; start aggressive, loosen after 4 weeks of clean traffic.
Effort
M 1–2 days.

R-PAY-05 · Chargeback exposure

High
Likelihood × Impact
High once charges start × Catastrophic for unit economics — chargeback fees are ~€15–25 each and Reloadly will not reverse the gift card.
Current state
No chargeback dispute handling, no proof-of-delivery archive.
Mitigation
For each successful order: archive (in Redis with 90-day TTL or in object storage) the IP, user-agent, device fingerprint, AVS/CVV result, 3DS auth code, recipient email, and timestamp. On dispute: Stripe accepts this in evidence. Set an internal chargeback-rate threshold (1.0%) and an alert.
Effort
M 1 day for archive; ongoing ops.

R-PAY-06 · Refund-flow abuse

Medium
Likelihood × Impact
Medium × Medium — "I never got the card" social-engineering ploy.
Current state
No refund flow exists; Reloadly fulfillment is irreversible.
Mitigation
Document a clear no-refund policy (R-LEG-02). On disputed claims, archive Reloadly's customIdentifier + delivery confirmation, manually verify, only refund after Reloadly confirms the card is unredeemed and can be cancelled.
Effort
S Policy decision + SOP. No code.

R-PAY-07 · Gift recipient is unverified

Medium
Likelihood × Impact
Medium × Medium — recipient-email manipulation is the standard pattern for stolen-card cashout (buy gift card, send to attacker-controlled email).
Current state
recipientEmail is collected, validated for format, never verified.
Mitigation
Optional MVP: hold the fulfillment for 60 minutes if customerEmail !== recipientEmail and the buyer is a first-touch. Send the recipient a "you have a pending gift" notification — only release after either (a) 60 min, or (b) recipient clicks a confirmation link. Caveat: hurts gift UX; defer if Radar + velocity catches enough.
Effort
M 2 days. Skip in MVP unless chargeback rate exceeds 0.5%.
